BattlEye: Stack Walking

Author: Musaed
Published: 2026
Category: Anti-Cheat Research / Kernel Internals

Overview & Motivation

One of the more interesting mechanisms encountered while reversing BattlEye is its kernel-side stack-walking and validation logic.

A primary reason for performing stack analysis is that code can execute from memory without necessarily appearing in the process's normal module list. Manual mapping is a classic example: an executable image can be manually mapped into memory without ever being registered as a conventional loaded module in the Process Environment Block (PEB) or kernel loader structures.

This makes the origin of execution a valuable telemetry signal. Rather than simply enumerating modules, the kernel routine can inspect active stack frames and determine whether the return addresses involved in execution correspond to expected, legitimate image bounds.

Core Concept

Stack walking verifies not just where an image claims to be loaded, but where instructions are actively executing from. An address residing outside known module boundaries serves as a primary signal for deeper control-flow analysis.

1. Obtaining the Target Thread & Queuing the Kernel APC

The routine begins by obtaining a reference to the target thread object. It compares the target thread ID against the current execution context and resolves the corresponding ETHREAD pointer via PsLookupThreadByThreadId:

C / Decompiled Target Thread Lookup 
CurrentThreadId = PsGetCurrentThreadId();

if (v20 != CurrentThreadId)
{
    LODWORD(CurrentThreadId) =
        PsLookupThreadByThreadId(v20, &Thread);
}

After obtaining the ETHREAD pointer, the driver allocates a context structure in pool memory and initializes a kernel Asynchronous Procedure Call (APC):

C / Decompiled APC Initialization and Insertion 
KeInitializeApc(
    AllocatedPool,
    Thread,
    0,
    UpdateCurrnetStack,
    0,
    0,
    0,
    0
);

KeInsertQueueApc(
    AllocatedPool,
    AllocatedPool,
    0,
    2
);

This design is significant because stack collection is performed directly in the context of the target thread via an APC, rather than attempting to walk an arbitrary foreign thread from the caller's context.

2. Collecting the Stack via RtlWalkFrameChain

Once the APC fires in the target thread context, execution reaches the StackUpdater callback routine:

C / Decompiled StackUpdater Routine 
LONG __fastcall StackUpdater(
    __int64 threadContext,
    __int64 flags,
    __int64 priority,
    __int64 *frame_pointer)
{
    __int64 frame;

    frame = *frame_pointer;

    *(_DWORD *)(frame + 2160) =
        RtlWalkFrameChain(
            (PVOID *)(*frame_pointer + 0x70),
            0x100,
            0);

    return KeSetEvent(
        (PRKEVENT)(frame + 0x58),
        0,
        0);
}

The critical operation in this routine is:

C Frame Chain Capture 
RtlWalkFrameChain(..., 0x100, 0);

The routine captures up to 0x100 (256) stack frames and records the resulting frame count directly in its context structure. It then signals an event (KeSetEvent) to notify the collector thread that the stack capture is complete.

3. Validating Frame Addresses Against Known Image Ranges

The collected return addresses are subsequently evaluated against known executable image boundaries. A simplified representation of the validation logic:

C / Decompiled Range Boundary Check 
_RDX = *(_QWORD *)&AllocatedPool[2 * v38 + 28];

if (_RDX < _RCX ||
    _RDX >= *(unsigned int *)(qword_1400171D8 + 32) + _RCX)
{
    // Address falls outside primary image range; walk auxiliary image metadata
    ...
}

The code tests whether the frame address falls within the expected base and size of known legitimate modules. If an address falls outside the primary image range, the routine walks additional image metadata.

Key Analytical Insight

An address outside a known module is not automatically treated as definitive proof of a manually mapped DLL. Instead, it marks an execution address that does not match expected module bounds, initiating the secondary validation and telemetry reporting pipeline.

4. Report Dispatching

After collecting the stack frames, verifying image bounds, and assembling execution metadata, the routine builds a structured report package. The final path dispatches the collected telemetry via:

C++ / Decompiled Thread Stack Report Dispatch 
BEDaisy::Report::ThreadStackReport(
    v127,
    v103
);

Or, depending on the internal reporting pipeline state:

C / Decompiled Alternative APC Stack Report Handler 
FnThreadApcStackReport(v127, v103);

Conclusion

The fundamental takeaway from reversing this subsystem is that the mechanism is most accurately characterized as stack-based execution-origin validation rather than simply a standalone check for manually mapped DLLs.

While manually mapped modules represent one source of execution addresses not backed by normal loaded images, dynamically generated code (JITs, shellcode, hooks, trampolines) can produce similar conditions.

Crucially, an unmapped or unexpected stack address serves as a signal rather than an immediate verdict. The subsequent boundary checks and metadata collection are what establish the context needed for report generation.
